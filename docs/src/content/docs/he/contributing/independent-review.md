שינוי בנתיב רגיש, כלומר בנתיבים ש-`.github/CODEOWNERS` מונה (הצפנה, כתיבה
לכספת, יומן הפרטיות, CSP ומדיניות אבטחה, ניקוי תוכן, הרשאות ועדכונים של
native), נסקר לפני המיזוג בידי מי שלא כתב אותו. זה חל גם על התיקונים
שרכבת אינטגרציה (`verify/*`) עושה כשהיא פותרת התנגשויות בקוד הזה: גם
ה-PR של הרכבת צריך סקירה. אדם עדיין מוסיף גם את התווית `human-reviewed`
(ראו [מתחזק שני](/he/contributing/second-maintainer/)). העמוד הזה הוא החלק
של הסוקר.

## הכלל

ב-`npm run pr:check` יש בדיקה בשם **Independent review of sensitive paths**.
כשקובץ רגיש השתנה, היא צריכה **קבלת סקירה** ש:

1. מציינת את ה-commit שבראש ה-PR (כל 40 התווים). דחיפה אחרי הסקירה הופכת
   את הקבלה ללא תקפה, וצריך סקירה חדשה;
2. הסוקר בה אינו הכותב (מסלול או סוכן אחר, או אדם), עם
   `"access": "read-only"`: לסוקר לא הייתה הרשאה לדחוף לענף;
3. מכסה כל קובץ רגיש ב-diff (`files`: נתיבים או תבניות של CODEOWNERS);
4. מונה לפחות מבחן התקפה אחד שהסוקר כתב או הריץ, עם התוצאה שלו;
5. אין בה ממצא בחומרה `critical` או `high` שעדיין `open`, וההכרעה היא
   `approve`.

עם `--pr <n>` הקבלות נקראות מהתגובות על ה-PR, והבדיקה נכשלת אם אין קבלה
תקפה. עם `--review <file>` (אפשר כמה פעמים) נבדק קובץ קבלה מול ה-`HEAD`
המקומי, בלי רשת. בלי אף אחד מהם, הבדיקה רק מזהירה.

## הקבלה

מפרסמים אותה כתגובה על ה-PR, בבלוק קוד שהשפה שלו היא `lumen-review`, או
שומרים אותה כקובץ JSON:

````md
```lumen-review
{
  "format": "lumen-review",
  "version": 1,
  "pr": 495,
  "head": "<ה-sha המלא של הראש שנסקר>",
  "author": "train-2",
  "reviewer": "S",
  "access": "read-only",
  "date": "2026-11-12T18:00:00Z",
  "files": ["/src/sync/e2ee/lan/"],
  "attackTests": [
    { "path": "src/__tests__/lanPreAuthAttack.test.ts", "result": "6/6 pass", "failsWithoutFix": 3 }
  ],
  "findings": [
    { "id": "E56-1", "severity": "medium", "status": "fixed", "summary": "…", "fix": "<sha או patch>" }
  ],
  "verdict": "approve"
}
```
````

| שדה | משמעות |
|---|---|
| `head` | ה-commit שנסקר. צריך להיות הראש של ה-PR בזמן הבדיקה |
| `author`, `reviewer` | מי כתב את השינוי ומי סקר אותו. חייבים להיות שונים |
| `access` | תמיד `read-only` |
| `files` | מה נסקר: כל קובץ רגיש ב-diff צריך להיות מכוסה |
| `attackTests` | ‏`path`, ‏`result`, ואפשר גם `failsWithoutFix`: כמה מהם נכשלים בלי התיקון |
| `findings` | ‏`id`, ‏`severity` ‏(`critical`, ‏`high`, ‏`medium`, ‏`low`, ‏`info`), ‏`status` ‏(`open`, ‏`fixed`, ‏`accepted`), ‏`summary`, ‏`fix` |
| `verdict` | ‏`approve` או `changes-requested` |

## איך הסוקר עובד

- מוציאים את הראש לקריאה בלבד (worktree מנותק, או `git show`), ולעולם לא
  דוחפים לענף שבסקירה.
- כותבים את מודל האיום: מי התוקף, מה הוא כבר יכול לעשות, ומה השינוי מוסיף.
- כותבים לו מבחני התקפה ומריצים אותם. כשמוצאים בעיה, מראים שהמבחן נכשל בלי
  התיקון.
- שמים את התיקון ב-patch או ב-PR נפרד לכותב, ואז מפרסמים את הקבלה לראש
  שנסקר.

## מי יכול לפרסם קבלה

נחשבת רק תגובה של חשבון עם הרשאת כתיבה לריפו: ‏`OWNER`,‏ `MEMBER` או
`COLLABORATOR` של GitHub. בריפו ציבורי כל אחד יכול להגיב, וקבלה של זר לא
פותחת את השער. ‏`pr:check` מציג אותה עם הסיבה. ה-`files` של קבלה צריכים
לציין מה נקרא. רשומה כמו `*`,‏ `**` או `/` שמכסה את כל הריפו לא נחשבת.

## קבלות חתומות

כל המסלולים של הסוכנים מפרסמים מאותו חשבון GitHub, ולכן החשבון לא יכול
להראות שהסוקר אינו הכותב. כשהקובץ `security/reviewers.json` נמצא בעץ, קבלה
נחשבת רק אם היא חתומה במפתח Ed25519 של הסוקר שהיא מציינת:

```bash
# פעם אחת לכל סוקר; המפתח הפרטי לא נכנס לשום ריפו
node scripts/review-sign.mjs keygen R --out ~/.lumen-review-keys
#   → מוסיפים את הרשומה שהודפסה תחת "reviewers" ב-security/reviewers.json
# לכל סקירה
node scripts/review-sign.mjs sign receipt.json --key ~/.lumen-review-keys/R.key.pem --comment
#   → מפרסמים את התגובה שהודפסה ב-PR
node scripts/review-sign.mjs verify receipt.json
```

החתימה מכסה את כל הקבלה חוץ מ-`signature`, עם מפתחות ממוינים, כך ששינוי
של שדה כלשהו אחרי החתימה שובר אותה. בלי `security/reviewers.json` הקבלות
נבדקות בלי חתימה, והדוח אומר זאת.

## הכיסוי של רכבת

‏`npm run review:coverage -- --train origin/verify/train-2 --base origin/main`
מציג כל PR רגיש שמוזג לרכבת (כותרות מיזוג `Merge #N …`, כולל רכבות שמוזגו
לרכבת) ואת ה-commits של הרכבת עצמה. לכל אחד הוא אומר אם יש קבלה שנחשבת
לראש שהרכבת מחזיקה. ה-commits של הרכבת עצמה צריכים קבלה לראש הרכבת
(`--train-pr <n>`). הקבלות מגיעות מהתגובות ב-PR-ים (`--live`) ו/או מתיקייה
של קובצי קבלה (`--receipts <dir>`). הפקודה יוצאת עם 1 מתחת ל-100%.
‏`--codeowners <file>` קורא את רשימת הרגישים מקובץ, לרכבת שעדיין אין בה
`.github/CODEOWNERS`.
