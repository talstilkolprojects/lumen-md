ל-Lumen יש מתחזק אנושי אחד (טל) וסוכני AI שפותחים את רוב ה-pull requests.
קוד שמגן על המשתמשים — הצפנה, כתיבה לכספת, יומן הפרטיות, CSP — לא יכול
להיות תלוי באדם אחד או להתמזג בלי שאדם קרא אותו. כאן כל מה שמתחזק שני צריך
ביום הראשון.

## 1. הרשאות (טל עושה, כ-10 דקות)

```sh
# הזמנה בתפקיד Maintain (מיזוג, תוויות, advisories; בלי הגדרות או מחיקה).
gh api -X PUT repos/talstilkol/lumen-md/collaborators/<login> -f permission=maintain
```

אחר כך טל מוסיף `‎@<login>` אחרי `‎@talstilkol` בכל שורה של
`.github/CODEOWNERS`, ב-pull request שהוא סוקר בעצמו (הקובץ עצמו הוא נתיב
רגיש). מאז GitHub מבקש את הסקירה שלכם בכל pull request שנוגע בנתיב רגיש.

## 2. מריצים הכול מקומית (בלי GitHub Actions)

הריפו לא מריץ GitHub Actions. כל בדיקה רצה אצלכם:

```sh
git clone https://github.com/talstilkol/lumen-md && cd lumen-md
npm ci
npm run typecheck && npx vitest run          # בדיקות יחידה ורכיבים
npm run build && npm run budget              # בניית production ותקציב החבילה
npx playwright test --project=chromium       # מקצה לקצה
bash tools/native-check/run.sh               # Rust ו-Java בלי רשת (אם קיים בענף)
npm run pr:check -- --base origin/<base> --pr <n> --no-size   # שער ה-PR, לפני מיזוג
```

## 3. סקירה של שינוי רגיש

`npm run pr:check -- --pr <n>` מציג את הקבצים הרגישים שה-pull request משנה
ונכשל עד שהתווית `human-reviewed` עליו, **ונוספה אחרי ה-commit האחרון**.
סוכנים אף פעם לא מוסיפים אותה: היא אומרת "אדם קרא את ה-diff הזה". קוראים את
ה-diff עם השאלות של התחום:

| תחום (הנתיבים ב-`.github/CODEOWNERS`) | שואלים |
|---|---|
| הצפנה (`src/sync/e2ee/`,‏ `src/collab/encryption.ts`,‏ `src/storage/vault/encrypted/`,‏ `src/lib/crypto*`, מחזיק המפתחות, חתימות) | רק WebCrypto ופרימיטיבים של הפלטפורמה, בלי הצפנה בכתב יד? nonce/IV אקראי וחדש לכל הצפנה, אף פעם לא פעמיים עם אותו מפתח? פרמטרי ה-KDF לא הורדו? מפתחות לא נרשמים ביומן, לא נשלחים ולא נשמרים גלויים? ההצפנה המאומתת (GCM) נבדקת לפני שימוש? |
| כתיבה לכספת (`src/storage/vault/`,‏ `src-tauri/vault/`,‏ `src-tauri/src/lib.rs`, תוסף ה-SAF של Android) | כל נתיב נבדק שהוא נשאר בתוך הכספת (`..`, נתיבים מוחלטים, symlinks)? הכתיבה אטומית (קובץ זמני ואז rename)? כשל משאיר את הפתק הישן שלם? |
| פרטיות (`src/ai/privacyLedger.ts`, יומן ה-worker,‏ `src/ai/policy.ts`, טלמטריה) | האם מארח, קטגוריה או כלל חדש מוציאים טקסט של פתקים, מפתחות או מידע אישי מהמכשיר בלי פעולה של המשתמש? ברירת המחדל עדיין מקומית בלבד? |
| CSP, כותרות ומדיניות (`src/build/cspEndpoints.ts`,‏ `public/_headers`,‏ `deploy/`,‏ `scripts/headers.mjs`,‏ `security/`) | אין wildcard חדש, `unsafe-*`, או מארח צד שלישי בלי רשומה ביומן? COOP/COEP לא השתנו בלי כוונה? |
| ניקוי תוכן וארגז החול של התוספים | HTML לא מהימן עדיין עובר ניקוי? ה-iframe של התוספים עדיין בלי `allow-same-origin`? |
| הרשאות native ‏(`src-tauri/capabilities/`,‏ `tauri.conf.json`,‏ `updates.rs`) | אין הרשאת `fs:`/`shell:` רחבה יותר? העדכונים עדיין חתומים ורק משרת השחרורים? |

כשהכול נכון: מאשרים (Approve) את ה-pull request ב-GitHub (האישור שלכם על
ה-commit האחרון מופיע בדוח של pr:check), ואז מוסיפים את התווית:

```sh
gh api -X POST repos/talstilkol/lumen-md/issues/<n>/labels -f "labels[]=human-reviewed"
```

אם מגיעים commits אחרי הסקירה, הבדיקה נכשלת שוב: סוקרים את ה-commits
החדשים, מסירים את התווית ומוסיפים אותה מחדש.

## 4. דיווחי אבטחה

דיווחים מגיעים כ-advisories פרטיים ב-GitHub ‏(`SECURITY.md`). שני
המתחזקים מקבלים אותם. אם טל לא ענה תוך 48 שעות, הדיווח שלכם: מאשרים קבלה,
ממיינים, מתקנים ב-fork הפרטי של ה-advisory, משחררים ומפרסמים.

## 5. מה רק הבעלים מחזיק היום

אלה נקודות כשל יחידות עד שהן משותפות או מופקדות; כל אחת היא צעד של הבעלים
(משימה W4.7):

- פרויקט Vercel והדומיין `lumen-md.vercel.app`;
- מפתח החתימה של עדכוני שולחן העבודה (minisign) והסיסמה שלו;
- חשבונות Apple Developer ו-Google Play ומפתחות החתימה שלהם;
- הרשאות admin בריפו ב-GitHub.

מומלץ: עותק חתום של כל מפתח במנהל סיסמאות משותף לשני המתחזקים (‏1Password
או Bitwarden עם "גישת חירום"), והרשאות admin למתחזק השני אחרי שישה חודשים
של סקירות.

## 6. מפתח חתימה שני

לכל מפתח חתימה צריך מחזיק שני, או מפתח שני תקף באותה מידה, כדי שמחשב שאבד
או אדם שנעדר לא יעצרו שום דבר.

| מה נחתם | היום | עם שני מתחזקים |
|---|---|---|
| הסקירה שלך והקומיטים | — | כל מתחזק חותם על קומיטים ותגיות במפתח SSH משלו: `git config gpg.format ssh`, ‏`git config user.signingkey ~/.ssh/id_ed25519.pub`, ‏`git config commit.gpgsign true`, ומוסיפים את המפתח ב-GitHub כמפתח **חתימה**. טביעת האצבע שלו נכנסת לטבלה ב-`SECURITY.md` („Maintainers and keys”). |
| תוספי הרישום (Ed25519, [מפתחות לחתימת תוספים](/he/plugins/signing/)) | המפתח של טל, אם הוגדר | **מפתח שני, לא עותק.** ‏`VITE_PLUGIN_TRUSTED_KEYS` הוא מפת JSON של טביעת אצבע ← מפתח, ולכן המפתחות הציבוריים של שני המתחזקים מהימנים זה לצד זה. כל אחד חותם במפתח שלו (`openssl genpkey -algorithm ed25519`), וכל אחד יכול לבטל את המפתח של השני במחיקת רשומה אחת. |
| עדכוני שולחן העבודה (minisign, ‏`plugins.updater.pubkey` ב-`tauri.conf.json`) | המפתח והסיסמה של טל | המעדכן סומך על מפתח ציבורי **אחד**, ולכן אין אפשרות למפתח שני. המפתח הפרטי והסיסמה שלו נכנסים לכספת החירום המשותפת (סעיף 7). כדי להחליף מפתח: משחררים גרסה אחת שחתומה במפתח הישן, וההגדרות שלה כוללות את ה-`pubkey` החדש. מאז הגרסאות נחתמות במפתח החדש. |
| ‏Android ו-iOS | החשבונות של טל | המתחזק השני מתווסף ל-Google Play Console ול-App Store Connect בתפקיד שחרור. מפתחות החתימה נכנסים לכספת החירום. |

כשהמתחזק השני מצטרף: יוצרים את המפתחות, מוסיפים את שתי טביעות האצבע
ל-`SECURITY.md`, ומוסיפים את `@<login>` ל-`.github/CODEOWNERS`. שני השינויים
נוגעים בנתיבים רגישים, ולכן המתחזק האחר סוקר אותם.

## 7. גישת חירום

אם אחד המתחזקים נעלם, השני צריך להיות מסוגל לשמור על המשתמשים: לשחרר תיקון
אבטחה, לבטל מפתח, להשאיר את האתר באוויר.

1. **כספת חירום משותפת.** משתמשים במנהל סיסמאות עם גישת חירום מואצלת, למשל
   Emergency Access של Bitwarden. חשבון פרימיום מגדיר איש קשר מהימן (לאיש הקשר
   מספיק חשבון חינמי). איש הקשר מבקש גישה, והיא ניתנת אוטומטית אחרי זמן המתנה
   שהמחזיק בוחר, אלא אם המחזיק דוחה אותה
   ([Bitwarden](https://bitwarden.com/help/emergency-access/)). בוחרים גישת
   **צפייה** עם המתנה של 7 ימים. בכספת:
   - מפתח minisign והסיסמה שלו;
   - מפתח ההעלאה של Android והסיסמה שלו;
   - פרטי הגישה של Apple;
   - קודי השחזור של Vercel ושל Cloudflare;
   - קודי השחזור של GitHub.
2. **ממשיך ב-GitHub.** טל מגדיר את המתחזק השני כ-**successor** של החשבון
   האישי שלו (Settings ← Account ← Successor settings ← Add successor), כדי
   שהמאגר יוכל להמשיך גם אם החשבון לא יכול
   ([GitHub Docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/maintaining-ownership-continuity-of-your-personal-accounts-repositories)).
3. **דיווחי אבטחה.** שני המתחזקים מקבלים כל advisory. אם אחד לא עונה תוך 48
   שעות, השני אחראי עליו (`SECURITY.md`).
4. **תרגול שנתי.** פעם בשנה המתחזק השני פותח את כספת החירום במצב צפייה, בודק
   שכל מפתח נפתח, וחותם על קובץ בדיקה במפתח minisign. אחר כך המחזיק מחליף את
   מה שנפתח.

## 8. תור הסקירה השבועי

פעם בשבוע אחד המתחזקים מריץ:

```sh
npm run review:queue -- --base verify/train-2 --out queue.md
```

הפקודה מציגה עד **חמש** בקשות משיכה פתוחות שמשנות נתיב רגיש ולא נסקרו בידי
אדם מאז הקומיט האחרון שלהן. הן מסודרות לפי תחום (קריפטוגרפיה קודם), ואחר כך
לפי גיל. לכל אחת התור נותן:

- את הקבצים הרגישים, לפי תחום;
- את השאלות מסעיף 3;
- את הבדיקות ב-`src/__tests__` שמייבאות את המודולים שהשתנו;
- **מקרי תקיפה** לנסות (בית מוצפן הפוך, nonce שחוזר, שם פתק עם `../`, קישורי
  `javascript:`...);
- את הפקודות להרצה.

הפקודה רק קוראת מ-GitHub. היא לא מוסיפה תוויות ולא כותבת תגובות.

היעד הוא זמן סקירה חציוני של **3 ימים לכל היותר**. בקשה שנשארת בתור יותר
משבוע היא הראשונה במפגש הבא.

**קריפטוגרפיה דורשת מישהו אחר.** בבקשה שמשנה נתיב בקטע *Cryptography*
של `.github/CODEOWNERS`, ‏`npm run pr:check -- --pr <n>` סופר את התווית
`human-reviewed` רק אם הוסיף אותה מי שהוא **לא בעל המאגר ולא כותב הבקשה**.
טל והסוכנים כתבו ובדקו את הקוד הזה בעצמם, ולכן הטעם הוא אדם שני.
