### RR14-469-1 (MEDIUM, from reading, not confirmed by a test): the review-11 DoS path is narrowed, not closed

Three gaps in the new rules:

**(a) The byte cap is checked only when a room is admitted** (`roomQuota.mjs:188-190`).
- `saved()` never checks it.
- So rooms admitted while they are small can each grow to MAX_ROOM_BYTES afterwards: 50 rooms × 4 MB per owner, against a "20 MB" cap.

**(b) "Only a non-creator protects" compares the /64-level owner value only** (`worker.mjs:262`, `joined`).
- A second address protects the room.
- So does another /64 of the creator's own /48.
- So the rule stops a lone address, but not an attacker with two addresses or one IPv6 /48.

**(c) The multi-room plan gives up too early** (`roomQuota.mjs:252-265`).
- It takes the smallest rooms in ascending order and stops at 32 (`:259`).
- If the 32 smallest unprotected rooms together free less than the need, it returns null. It does that even when somewhat larger rooms, each still under the need, would free it together.
- So 32 tiny unprotected rooms, from anyone, including near-empty legitimate rooms, make every multi-room plan fail.

**Combined:** a store held over its cap by protected rooms that grew after admission, plus a few dozen tiny rooms, could again refuse every new room. That is RR11-469-1's outcome. I did not build a test for the combination.

**Fix:**
- Enforce the per-owner byte cap on `saved()` too, either by refusing the write or by making overage evictable first.
- Compare the /48 owner value as well when deciding who counts as "not the creator".
- Build the plan from the largest rooms below the need (descending order), or skip rooms too small to matter, so that 32 tiny rooms can't block it.

### RR14-469-2 (LOW, from reading): canEvict calls that don't count

**Where:** `makeWay`, `worker.mjs:652-667`.

**What happens:**
- `calls += plan.length` runs only when every room in a plan agreed.
- The `canEvict` RPCs sent to rooms that agreed inside a plan that then failed are never counted.

**Worst case:** 256 failed plans × up to 32 rooms is roughly 8,000 room RPCs for one admission attempt. That costs time and Durable Object requests.

**Fix:** count every `canEvict` against a budget, or stop asking a plan's rooms at the first refusal.

### RR14-469-3 (INFO)

- **Test scale:** see the caveat above. V1, V2 and V7 need `COLLAB_STORED_BYTES_PER_ADDRESS` re-scaled to test what their names say.
- **Charging refused attempts:** this was decided. I can't show harm to honest users from the code alone. The only case I see is honest retries during a store-full refusal using up an honest address's 20 a day; it needs RR14-469-1 to happen first.
- **In-use budget (256):** a room held open costs one of 256 refusals, and is then skipped for an hour.
  - So blocking one admission takes 256 rooms held open.
  - Those rooms must be unprotected and must sort before the rooms that could make way.
  - That is expensive. I'm not flagging it beyond RR14-469-2.

**Verdict:** changes-requested, for RR14-469-1. It is from reading; a confirming test at a re-scaled store would settle it either way.

**Popup-capable frames are tracked from first sight** (`latchPopups`):
- The observer's decision latches a frame while the switch is off if its sandbox has `allow-popups`, or if it has no sandbox and holds another site's page.
- At the switch, every latched frame that isn't among the frames present is recorded.
- Frames with nothing loaded are not latched (`:329`): no `srcdoc` and no `src`, or `src` set to `about:blank`. This is fine. If such a frame is navigated by script, it is same-origin, so its `window.open` is tracked, and it is counted while it is present.

**X6 disclosure: accurate.**
- `airplaneCertificate.ts:33` now says that a frame inside a closed declarative shadow root (`setHTMLUnsafe`, `parseHTMLUnsafe`) is out of reach.
- X6 shows exactly that: no FRAME and no POPUP is recorded.
- It remains latent: no app code calls these APIs.

### RR14-451-1 (INFO, from reading)

- **Where:** `MAX_LATCHED = 500` (`airplane.ts:321`) drops the oldest latch once there are more than 500.
- **Effect:** a note that mounts more than 500 popup-capable frames in a session could lose the latch for the frame that opened a window. Meanwhile the certificate says "from the moment it was made".
- **Fix:** count the dropped latches, and record one POPUP for them at the switch.

**Verdict:** approve.
