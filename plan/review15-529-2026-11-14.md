## U2: is any hang or lost wakeup left?

None found.

**How the wait works** (`workspaceIndex.ts`, `wakeOnUnlockOrMove`):
- It registers the wake before it reads the state, then loops.
- It wakes on unlock, on `dropIndex`, on every structural event and on every `ensureIndex` call.
- After each wake, a build whose epoch or vault moved returns. Otherwise it registers again and re-reads the state.

So an unlock that lands between any two steps is still seen, either by the listener or by the next read.

## T7: can the views' wait hang, or be bypassed?

**Bypass: no.**
- `indexedFiles()` returns `[]` while `cache.verify` is set. `byPath` and `verify` are set in the same synchronous step, and the in-thread fallback after a worker death runs inside the check.
- Once the check is done, `indexVersion()` moves (u6), so cached views re-derive. The deleted note is not shown at any point.
- The callers that weren't switched to the checked wait (`hoverPreview`, `RelatedPanel`, `graphData`, `UnlinkedMentions`, `PropertiesPanel`, `tagsIndex`) just see `[]` during the check. That costs some UX for a moment but leaks nothing.
- The other plain `ensureIndex()` callers (`ai/embeddings`, `QueryBlock`, `daily/morning`) don't read `indexedFiles()`.

**Hang: V3 (info).** A view awaiting `ensureIndex(false, {checked: true})` waits as long as the listing does:
- While the vault is locked, it waits for the unlock, which is the intended behaviour.
- If a backend's listing never settles, the view hangs (u5 FAILs). A listing that errors fails the check closed and the view gets an error.

A listing that never settles is a backend bug. A timeout on the check, treated as a failure, would cover it.

## S3: the size fallback for old records

**What holds:**
- `sameNote` requires the same mtime and, when both sizes are known, the same size.
- The size is the UTF-8 length of the text. For encrypted files the listed size is `plainSize`, which agrees: the sealed open still takes every note from the snapshot (`fromSnapshot N`).
- A size that doesn't match only makes the index re-read the note, so a mismatch can never keep stale text.

**V1 (low), plain records written before sizes:** these are trusted on the mtime alone until they are rewritten (`sizes` is optional in `decodeSnapshot`). An equal-mtime edit of another length keeps the stale text (u7 FAILs).
- The PR documents this fallback.
- The record is rewritten, with sizes, after the next change.
- It affects plain vaults only, and it is about integrity, not confidentiality.

**Old sealed v2 manifests without sizes (from rounds 2–3)** are **refused** instead: `decodeManifest` requires `sizes` (u7b: `fromSnapshot 0`, `read 8`, correct text). That is safe and costs one full read. It also means the PR body's line "a record written before the sizes still opens" is true only of plain records.

**Fix for V1, optional:** treat a record without sizes as unchecked, so its notes are re-read once, or drop it.

**V2 (info, inherent):** equal mtime and equal size with different content is still kept (u8). No backend lists a content hash.
