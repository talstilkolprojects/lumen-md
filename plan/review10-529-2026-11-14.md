## 1. Is S1 really closed?

**For the path it named, yes.**
- `snapshotMode` returns `null` for an unavailable backend (`workspaceIndex.ts:275`).
- It returns `null` for `none` when `filledEncrypted` is set (`:277`).
- It returns `null` for anything that isn't `unlocked`.
- `fillingEncrypted()` counts unavailable or unknown as encrypted (`:288`).

rr9 (a) passes, and so do the PR's "unavailable" and "decrypted behind the index" tests.

Other paths:

| Path | Result |
|---|---|
| **Vault switch (T1, high)** | **Plaintext written.** |
| Lock during the idle window | Safe. The mode is decided when the timer fires: locked gives `null`. A save already sent with keys still seals. Covered by the PR's "locked" test. |
| Worker restart | Safe. In (w3) the worker is killed right after it answers the restore. The in-thread fallback restores through `loadSnapshot` with keys, refuses the swapped body, reads every note, and the next save is sealed. |
| Mode change in another tab (T3, medium) | **Plaintext written.** |
| Conversion race, S4 (T6, low) | **Plaintext written** when the save is still in flight. |

### T1 (high): an encrypted vault's notes saved in the clear after a vault switch

**Where:**
- `cache.filledEncrypted` is set only in `build()` (`workspaceIndex.ts:361`).
- A vault switch does not rebuild the index. `location.ts:299-305` `activate()` only announces a structural change.
- `refresh()` and `applyChanges()` (`:454`, `:502`) then fill the same index from whatever vault is active.

**Scenario:**
1. The index is built from plain vault P (`filledEncrypted = false`).
2. The user opens encrypted vault E and unlocks it. `refresh()` reads E's notes into the same index and schedules the idle save.
3. The user switches back to P within about 5 s.
4. `snapshotMode()` sees P is `none` while `filledEncrypted` is false, so it chooses plain mode. The worker then saves **E's paths and texts in the clear, under P's id**.

Any edit in E followed by a switch within the idle window does the same.

**Test:** `rr10 main (a)` FAILs:
```
E text indexed: "# e 1\nESECRET-1 …" | sealed while E: true | after switch to P: sealed false | ESECRET in clear: true | {"v":1,"vault":"vault-P","paths":["e/n9.md",…
```

**Fix:**
- Minimal: set `filledEncrypted = true` whenever notes are read while `vaultEncryptionReady() !== "none"`. That covers `indexFile`, `applyChanges` and `fillEngine`.
- Better:
  - Record the vault id the index was filled from.
  - Clear the engine and `byPath` (a rebuild, with `epoch++`) when `getVaultBackend().id` changes.
  - Never save an index under a vault id other than the one it was filled from.

  This also fixes T4 on a switch.

### T3 (medium): encryption turned on in another tab

**Where:**
- The gate caches its "plain" result (`vault/index.ts:82`). It looks again only after a read returns ciphertext (`:110`).
- There is no BroadcastChannel or other cross-tab signal for turning encryption on or off.

**Scenario:**
1. Tab 1 filled its index while the vault was plain.
2. Tab 2 converts the vault and drops the snapshot.
3. Tab 1's next idle save, for example after an edit, writes the whole index in the clear.

**Test:** `rr10 main (d)` FAILs. It emulates tab 1's module state: the gate still caches plain, the state is "none", and there is no sealer.
```
vault file now ciphertext: true | record after tab 2: null | tab 1 save: plain true | TABSECRET in clear: true
```

The plain-mode logic is the same class as #420, but it contradicts the PR's "never in the clear". Outside #529: tab 1 also writes the edited note itself to the vault as plaintext.

**Fix:**
- Before any plain save, re-stat the header (`refreshVaultEncryption()` plus `ready()`), or
- announce encryption on and off on a BroadcastChannel.

### T6 (low): S4, a queued plain save lands after the drop

`enableEncryption` calls `migrateStores("seal")`, which runs `dropSnapshot()` on the main thread (`session.ts:393`). A plain `snapshotSave` that is already in the engine queue runs after it.

**Test:** `rr10 main (c)` FAILs. It holds the engine's save the way a busy worker would.
```
after conversion: null | after queued save landed: plain true | CONVSECRET in clear: true
```

The plain record stays until the next sealed save, or until the next open refuses it. The window is narrow, and the text was plain in the vault moments earlier.

**Fix:**
- Drop through the engine's queue, so the drop is ordered after any queued save, and drop again once the conversion has finished, or
- have the worker refuse a plain save after the encryption mode changed.

## 2. Swap, mix, truncate, replay, downgrade

These all hold (S2, info). AAD = `["lumen-rest/1/snapshot", sv, vaultId, vault, part, sid]` (`snapshotSeal.ts:117`). It is rebuilt from the caller's expected values plus the record's `sid`, and the `sid` is covered by each part's HMAC (`:180`).

`rr10 main (h)` and the PR suite show all of these are refused:
- the parts swapped;
- either part from another seal, with either `sid`;
- `sid` changed;
- a key holder's short body (n−1 texts for an n-entry manifest);
- truncated ciphertext;
- a record for another workspace, or under other keys.

Downgrades are refused too:
- a round-1 v1 record (one part) fails on shape;
- v2 with `sv: 1` fails on version;
- a sealed record read without keys, and a plain record read with keys, are both refused.

Through the real worker:
- (w1) a body from another seal of the same vault (valid MAC, other `sid`) is refused, the record is dropped, all 30 notes are read and the search is right;
- (w2) a flipped body is refused;
- (w4) a genuine open comes from the snapshot, with nothing plain in IndexedDB.

Replaying a whole older record of the same vault is still accepted (rollback). The PR's argument that this is harmless depends on the check, and see T2 and S3 for where that check falls short.

The only remaining **writer-side** way to go from sealed to plain is the mode residues T1, T3 and T6. The reader side always refuses the other kind.

## 3. Trusting the manifest before the check

**Text queries wait for the check (holds):** `rr10 main (e2)`. With a rolled-back record and the listing held back:
- search, backlinks and tasks don't show the note deleted while closed;
- `indexedNoteText` returns n3's current text and `null` for the deleted n4.

The `defer` and `snapshotBody` ordering is correct in the worker: the body work runs before the next request.

### T2 (medium): the check fails open

**Where:**
- `verifySnapshot`'s `catch` (`workspaceIndex.ts:419-423`) only resets `checkedAt` and then clears `cache.verify`. Every caller waiting in `verified()` (`:98`) then goes ahead on the **unchecked** snapshot.
- `indexedNotes` and `indexedNoteText` (`:652`, `:667`) never call `ensureIndex`. They keep answering unchecked text for as long as the folder can't be listed (the editor, embeds).

**Test:** `rr10 main (f)` FAILs. A rolled-back record is put back, and the listing throws.
```
search for a deleted note's text: ["f/n4.md",…] | n3: "# f 3\nOLDWORD-3 …" | n4 (deleted): "# f 4\nOLDWORD-4 …"
50 ms later, still unlistable: n4 (deleted) text: "# f 4\nOLDWORD-4 …"
```

So deleted or old content is shown as current, which is exactly what the rollback argument says can't happen. This is integrity, not confidentiality: no one outside learns anything.

**Fix:** after a failed check, keep the index "unchecked":
- `verified()` retries the listing, or rejects; and
- `indexedNotes` goes through `ensureIndex`; or
- the trusted entries are marked `modified = 0`, so nothing unchecked is answered.

### T7 (low, documented): deleted notes in `indexedFiles()` before the check

**Where:** until the check, `indexedFiles()` (`:608`) holds notes deleted while the app was closed, or brought back by a rolled-back record. They carry their name, tags, frontmatter and links, so the tags panel, the graph and `[[` completion show them for the length of the check.

**Test:** `rr10 main (e)` FAILs:
```
{"name":"Merger with Acme.md","tags":["acquisition","confidential"],"links":["Board minutes"]}
```
After the check the note is gone.

The data reaches no one but the unlocked user, and the PR body says summary views can show the old state for a few seconds.

**Fix:** state it in the user docs, or have summary views apply removals only after `indexChecked()`.

### S3 (low): trusting the mtime alone

**Test:** `rr10 main (g)` FAILs. With an equal mtime, `n3` keeps the snapshot's old text after the check (`fromSnapshot 10, read 0`).

This rule is unchanged, and the size in the manifest is still owed.

## 4. Lock and vault switch: is the in-memory index cleared?

**No.**

### T4 (medium, pre-existing #420)

**Where:** `lock()` (`session.ts:209`) dispatches `LOCKED_EVENT`, but `workspaceIndex` doesn't listen to it. The main thread keeps every summary (paths, tags, links, frontmatter), and the worker keeps every text.

**Tests:**
- `rr10 main (b)` FAILs. Right after lock, `indexedNoteText` returns the text, search returns 5 hits, and 10 summaries are still held.
- `rr10 worker (w5)` FAILs. The real worker still returns n5's text.

Anything running in the page, for example a plugin or a shortcut behind the unlock overlay, can read it.

**Fix:** on `LOCKED_EVENT` and on a vault switch, clear the engine and `byPath` and bump `epoch`. #529 makes this cheap: a reopen from the sealed snapshot takes 0.37 s.

### T5 (medium, pre-existing 11.4, outside #529's diff)

**Where:** `lock()` clears only `current`'s keys (`session.ts:209-214`). The other sessions in `sessions` stay unlocked.

**Test:** `rr10 main (i)` FAILs:
```
after lock, E1 read without passphrase: "# i1 1\nFIRSTSECRET-1 …"
```

**Route:** this goes to the 11.4 / #472 owners and is not counted against #529.

**Fix:** lock every session, or forget the other sessions' keys on a vault switch.
