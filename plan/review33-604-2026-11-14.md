## The fix, as read

1. **`withEngine`'s refill** (`workspaceIndex.ts:299-326`) records the epoch and vault of its request and passes `moved(at, vault)` to `fillEngine` as the stale guard. When the guard trips, it calls `discard()`, throws, and does not retry `fn`.
2. **`saveSnapshotNow`** (`:537-549`) checks the generation, epoch and vault before `snapshotMode` and again inside the engine request, immediately before `eng.saveSnapshot`. It uses the key it captured.
3. **`refresh()`** takes `at = epoch` at its start (`:781`) and gives way at `:826` before `applyChanges`.

## Can the abort leave the engine half-filled for the active vault? Yes: Z7 (low)

**What happens:**
1. The refill gives way because a switch, a lock or a drop moved the epoch, and that drop has already cleared the engine.
2. The refill then calls `discard()` (`:322`) anyway, which clears the same in-thread engine again.
3. If a build for the vault now active ran during the refill (here, the user opened E, and any query builds it), that clear empties E's freshly filled engine.
4. `builtAt` and `byPath` stay set, so `ensureIndex` sees nothing to do. Revalidation re-reads only changed notes. Until the next switch or restart, E's search returns nothing.

**Test:** rr33 (v1).
```
E built during the refill: true | E hits after the abort: 0 | after another ensureIndex: 0 | plain ESECRET writes: 0
```
At `6c4e209be2` the same interleaving also gives 0 hits for ESECRET. There the refill's late upserts overwrote E's notes with P's text, which is a cross-vault integrity mix. #604 turned that into an empty index, which is better but doesn't heal.

**Fix:**
- Don't discard when the epoch moved: the drop already cleared the engine, and the stale guard stops any later post.
- When only the vault moved, as with a switch that skipped the notification, call `dropIndex()` instead of `discard()`, so the next use rebuilds.

## Other remaining IndexedDB writes

None found.
- The only writer of a snapshot record is the engine's `snapshotSave`. Every route to it now passes `current()` synchronously right before it posts.
- The engine runs requests one at a time, so a save posted before a drop saves the earlier vault's own text under its own key, in its own mode, and nothing else.
- `loadSnapshot`'s delete and `dropSnapshot` only remove records.
