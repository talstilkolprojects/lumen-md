## #607: LAN services host → peer

| Question | Answer |
|---|---|
| Mutual authentication | **Holds.** The peer proves `HMAC(pairing, "…|peer|hostNonce|peerNonce")` and the host proves `"…|host|peerNonce|hostNonce"` (`rpc.ts:60`). The peer sets `provenKeys` only after it has checked the host's tag, and it answers no service before that (`rpc.ts:397`, "auth"). The host asks only `authed` connections (`rpc.ts:325`). H1–H3: an unproven peer, or one with another vault's keys, gets no link either way, and its services run 0 times. |
| Replay and reflection | **Holds.** Role labels keep one side's tag from working as the other side's, and a fresh nonce on each connection keeps an old tag from being replayed. Answers are matched by `rs` against requests the host actually made (H4). Waiting calls fail as soon as the link closes (H5). |
| Can a peer that never paired make the host send it dictation audio? | **No.** Offers go only to `peerLinks`, which contains proven peers only. The audio is sealed with the vault keys and bound to its direction and request id (V3). |
| Does audio or text leave the LAN? | **No.** `desktopOffload.ts:193` and `:341` now refuse a link with a `null` address, which closes review 6's RR6-520-3. The links are #392's LAN-only WebRTC. |
| N3 (info) | The proof is not bound to the WebRTC channel: `proofData` holds no DTLS fingerprints. That is fine while the codes travel out of band, but not once #609 sends them over the network (L1). |
| N4 (info) | A peer's reply keeps any `rq` or `id` its service put in the header. Routing uses `rs`, so this is harmless; strip them for symmetry with the host side. |

## #609: mDNS and the rendezvous

### L1 (medium): pairing codes over plain TCP, and a proof not bound to the channel

**Where:**
- The pairing codes (SDP, which carries the DTLS fingerprints) now travel over plain TCP.
- The host is found through mDNS names, and nothing authenticates them.
- The passphrase proof (`rpc.ts` `proofData`) does not cover the channel's fingerprints.

**What changed:** with QR or text codes, the user carried the codes from one screen to the other, and that was an out-of-band check. On this path nothing replaces it. A device on the same network can end up between the user's two devices without the proof failing.

**What it gets:** the vault's payloads stay sealed. So such a device gets roughly what an untrusted storage provider gets:
- ciphertext and timing;
- the ability to drop or rewrite bucket operations on an authenticated link;
- standing as a "proven" peer.

**Fix:** either or both of these:
- **Bind the proof to the channel:** each side puts the local and remote DTLS fingerprints it actually uses into `proofData`.
- **Show a short comparison code** on both screens before the link is trusted.

### L2 (low): first come, first served, and duplicate names

**The token:** it is handed out with the offer to whoever asks first, so it is not a secret from others on the network. The first device to take the offer, or to answer with an observed token, uses the pairing up, and the user's device gets `ERR used`.

**Is the code guessable, or reusable once intercepted?**
- **Guessable:** no. The token is 128 bits from std's `RandomState`, which std keys from the OS random source, and the compare is constant-time.
- **Reusable:** no. The offer is handed out once and only one answer is accepted.

**Duplicate names:** devices that announce the same name are collapsed into one (`lib.rs:242`, `discovery.ts:123`). The user can't see that two devices claim the same name.

**Fix:**
- Show every device that answers, and warn when a name is duplicated.
- On `ERR used`, start a fresh offer with a new name.
- With L1's binding in place, a wrong first answer simply fails the proof.

### L3 (low): the port's lifetime

**What works:** the rendezvous closes on stop, on an answer, and when a new pairing starts (`lan_discovery.rs`). When the dialog closes, the web side stops it within one poll (≤ 400 ms).

**What's missing:**
- The Rust side has no expiry of its own. If the web view is reloaded or crashes mid-pairing, the port stays open with the offer until the app quits.
- Each connection gets its own thread, with no limit. Each thread is bounded by 5 s timeouts and a 64 KiB line.

**Fix:** a Rust-side expiry (for example 5 minutes) and a cap on concurrent connections.

### L4 (holds): address rules

- **The rule:** private IPv4, link-local and loopback; for IPv6, loopback, `fe80::/10`, `fc00::/7` and v4-mapped addresses. This matches `address.ts`.
- **Where it applies:** to mDNS answers, to the rendezvous accept, and on the web side.
- **Which address is used:** the joiner connects to the answer's source address, not to the SRV target.

### L5 (holds): parsing malicious packets

- **Bounds:** messages of at most 9000 bytes, names of at most 255 bytes, and compression pointers that may only point backwards, so a pointer cycle can't keep a name growing past the length cap. TXT and rdata lengths are checked.
- **Robustness:** 200,000 hostile inputs, half random and half mutations of a valid answer: no panic, and allocation is bounded by the message size.
- **What is announced:** nothing about the user or the vault, only a random `Lumen-XXXX` and `TXT v=1`.
- **The FFI** for `SO_REUSEPORT` (`net.rs`) closes the descriptor on every error path.
