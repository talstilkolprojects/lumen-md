## Findings

### S13-1 — MEDIUM — G4 is still open once the issuer has confirmed, or once its hold has ended

**Test:** `rr13/r13-1-g4-after-confirm.test.ts` gives 0/3. In all three cases the users are honest and the symbols really match.

**(a) Two-way, cancel after "They match".**
- A's user presses *They match* first. A posts `confirm-issuer` and shows "waiting".
- The user then cancels on A and revokes the phone.
- `cancelPairing` deletes A's objects best-effort (`engine.ts:1349-1351`) and releases the hold at once (`:1255`). But the storage keeps the confirmation and puts it back.
- The laptop, which the storage keeps on the epoch-1 view, confirms:
  ```
  A confirm: waiting | A after cancel revokes: epoch 2 | laptop confirm: done | laptop verified: true | uploaded: 1 | revoked phone reads: ["a.md","new.md"]
  ```

**(b) and (c) One-way, no cancel, either confirmation order.**
- The joiner's window is `pair()` + `PAIRING_TTL_MS` (`engine.ts:1292`). The issuer's hold ends at code + TTL.
- The laptop enters the code at 1:50. A's hold ends at 2:00, and A revokes at 2:05 (a natural "pair the new laptop, then remove the stolen phone" sequence).
- The laptop's confirmation at 2:35 commits on the epoch-1 view, and the phone reads `new.md`.
- Two-way is not affected here: the joiner's window ends at request + 5 min, which is before the answer + 5 min hold.

**Why it matters.** Spec §6a and `docs/src/content/docs/sync/e2ee-keys.md:61-62` say "an answer or code used after that can't be confirmed any more, so it pairs nothing". The N3 hold exists so that no key change happens while a pairing can still commit. That holds on neither path. The adapted r7-4.sas passes only because A cancels *before* confirming.

**Fix:**
1. The joiner's window should end when the offer expires: the code's `issuedAt` + TTL, or the answer's `answeredAt` + TTL. It must never run past the issuer's hold.
2. Have the issuer confirm last: it posts `confirm-issuer` only after a valid `confirm-joiner`. Once posted, it keeps the hold for the joiner's whole window, `cancelPairing` included. If that isn't wanted, say plainly that a cancel after *They match* on this device doesn't stop the other one.
3. Add rr13-1 as regression tests.

### S13-2 — LOW — the test helpers can hide failures

- **`pairConfirmed` returns quietly when the joiner shows no symbols** (`src/__tests__/helpers/e2ee.ts:92`). That branch exists for the "the device needs nothing" case, but it would also hide a comparison that never started.
  - In an instrumented copy (`/home/claude/w-rr13-544p`), the branch was never taken across e2eeFifthReview, e2eeThirdReview, e2eeRekeyIntegrity, e2eeSync, e2eeSeventhReview and e2eePairingSas. So nothing is hidden today.
- **`relayBetween` copies every missing object both ways** (`:113`), not only the comparison objects. The "withheld copy" tests therefore also receive the other world's manifests and blobs.
  - With a relay limited to `lumen-pair-*` objects, e2eeSync (40/43) and e2eeThirdReview (10/10) give the same results.
- **Fix:** have the helper take the expected outcome, and relay only `lumen-pair-*` objects.

### S13-3 — INFO — the protocol checks pass

`rr13/r13-2` gives 5/5 and `r13-3` gives 3/3.

| Question | Result |
|---|---|
| Commitment order: who commits first? | One-way: the issuer commits in the code, and the joiner's key goes in the clear only after that. Two-way: the joiner commits in the request, and the issuer's key travels in the answer. A reveal that doesn't match its commitment is ignored (`(b)`). |
| How many guesses does a man in the middle get? | One. That holds even with the pairing key and the storage: a second swapped reveal doesn't change A's symbols (`(a)`), because `i.sas` is fixed on first read. The attacker can compute A's side but not the laptop's, and the laptop aborts on the forged issuer tag. I also argued through the case where the attacker controls both hand transfers: its keys are fixed before the other device's key is known, so the chance is still 2^-30. |
| Is the transcript complete? | Yes. It binds flow, vaultId, epoch, ringRev, ringDigest, counter, digest, session, answer, nonce and both keys. The session and answer hashes cover `issuedAt`, `answeredAt` and every body field. Each side builds the transcript from what it acts on: the joiner from the offer, the issuer from the anchor it stored. |
| Confirmation MAC reflection or replay? | Refused. The two roles use separate HKDF keys, so the joiner's own tag re-labelled as the issuer's fails. A session-1 confirmation replayed into session 2 is refused. The compare (`equalBytes`) is constant time. |
| Downgrade to the old versions? | Refused. A code-3 message with a valid MAC under its own label, and a v3 body under the v4 prefix, are both refused. A v4 code that commits to a key nobody holds never completes. |
| Storage withholding or reordering? | Withholding fails safe: nothing pairs. Reordering doesn't help: the issuer reveals only after it has read the joiner's key, and the joiner checks the commitment. |
| Does the abort path record nothing and restore the hold? | Yes. The joiner's state is byte-identical afterwards, no objects are left, and the hold returns to its earlier value. A second code plus a reject keeps an earlier confirmed pairing's hold (`r13-3 (c)`). |
| G3 and K5 | No code is issued during a stalled revocation (`r13-3 (a)`). A cancel plus a re-key ends the issuing session (`(b)`). `liveIssuing` refuses after any keyring change. |

### S13-4 — INFO — the issuer can say "done" under a man in the middle

- If the issuer's user taps *They match* without looking, A accepts the attacker's `confirm-joiner` and shows "Paired".
- Nothing is committed on A, and the real laptop aborts.
- This needs no code change. The usability doc could add a line about it.

### S13-5 — INFO — K6 conflicts with this PR

- K6 (#399 at `dd6d757786`) rewrites `pairingCode` and `answerPairing`: a Web Lock, a re-read of the stored state, and adopting another tab's keys. #544 rewrites the same functions.
- On the rebase:
  - capture `prevUntil` from the **re-read** state;
  - keep `liveIssuing`'s keyring check after K6's key adoption;
  - re-run rr13 and rr9-3.
- The issuing and joining sessions live in memory per tab, so another tab can't confirm this tab's code. That fails safe.
- I check this against K6's code in review 16.
