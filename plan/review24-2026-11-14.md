## #563, B1: the TTY plus typed-yes approval

**Fixed for what B1 named:**
- No tool answer names an approval command any more. The answers say that only the user can approve.
- `approve --all` is removed.
- Approval is per id or per `--client`, after each diff, with a typed "yes".

**Can it be piped or scripted?**
- **Piped:** refused. `printf yes | lumen mcp approve --client evil-app` prints the no-TTY message and writes nothing.
- **Scripted: yes (B1r, low).** `printf 'yes\n' | script -qec "lumen mcp approve --client evil-app --vault V" /dev/null` gives the command a pty, and the piped "yes" is accepted. That wrote the other client's change to `notes/plan.md`. The setup is in `$S/rr24/tty/`, and the log is above in this review's run.

**Why it is low:** an agent with a shell can also edit the note directly, so the CLI was never a boundary against it. But `cli.ts:47` and `lumen.ts:7` claim that an agent's shell cannot approve, and that is not true.

**Fix:** reword the claim as "stops an agent from approving by accident", and optionally allow approval in the app only.

## #601, C1–C5

### C1: fixed

**What changed:**
- Descriptions and schema text are withheld unless the server is marked `trustDescriptions`. When it is, they are cleaned, capped at 300 characters and labelled.
- Offering MCP tools taints the run from its start (`offeredBy` → `runtime.ts` taint).
- rr21 b1 passes.

**Trusted-description marking:** a server can't set `trustDescriptions` itself, because it is the user's config. Even with it set, the run stays tainted, so a write still needs approval.

**Residue:** tool names (≤ 128 characters of `[A-Za-z0-9_.-]`), property names and short enum strings still reach the model. That is a tiny channel, in a run that is already tainted.

### C2: fixed

**What changed:** `networkTarget` makes `describeNetworkCall` name the MCP server's URL and bind the fetch to it.

**From code reading:** `boundFetch` accepts the endpoint exactly, `endpoint/…` or `endpoint?…`. So look-alike hosts and paths are refused: `…/mcpx`, `far.example.evil.com`, and `evil.com/?…far.example`.

**Caveat:** there is still no production transport. The binding holds only if the caller builds the transport on `ctx.fetch`.

### C3: fixed for blocking; residue C3r (low, from code reading)

**What changed:**
- Stdio servers count as remote in airplane mode and under local-only AI, unless the user marks them offline (`servers.ts:122`). rr21 b4 passes.
- `npx -y` is removed, Knessy now runs as `python3 -I`, and the HTTP transport sets `redirect: "error"`.

**C3r:** that remote status is used only for blocking.
- **Where:** a non-offline stdio server's tools keep the `read` scope (`tools.ts:71`) and get no `networkTarget` (`tools.ts:86`).
- **Effect:** under local-first or cloud, a call that carries the user's text gets no network gate, no ledger entry and no untrusted approval. Only the per-tool "ask", which is the default, stops it.
- **Fix:** give non-offline stdio tools the network scope too.

### C4: fixed

**What changed:**
- `resource` (RFC 8707, a canonical URI) is sent and required.
- The metadata must advertise S256.
- `checkAuthServerMetadata` requires the issuer to equal the discovery origin. The caller has to call it.

**(issuer, resource) keying:**
- The keys are `JSON.stringify([issuer, canonicalResource(url)])`.
- Equivalent spellings of one URL map to one key: case in the scheme and host, the default port, a trailing `/`.
- Another path, host or issuer maps to another key.

**Still owed when the flow is wired:** sending `resource` again at the token endpoint, and storing tokens in the secret store.

### C5: fixed

- Names now carry an FNV hash of the `(server, tool)` pair, and duplicates within one server are dropped.
- Server ids are chosen by the user, so one server cannot reach another server's name prefix.

## #599, D1–D3

### D1: fixed, with the git-vault rule

**What changed:**
- Only the starters run without asking. A vault skill asks once per version on this device.
- A vault with `.git` at its root passes `sharedFrom` (`ui.ts:38`), so its skills are guarded and tainted on every run.

**Residue:** a vault that is a subfolder of a repository, or a synced or downloaded folder without `.git`, counts as the user's own. After its one question, such a skill runs unguarded and untainted. That is acceptable: the consent is per version.

**Docs:** `docs/ai/skills.md` still says vault skills run without asking. The author notes this.

### D2: fixed

- The fingerprint is SHA-256 over name, description, tools, metadata and body.
- An outside skill's description is guarded together with its body.
- Unknown tool names are counted, not quoted.

### D3: partly fixed (still medium)

**What works:** `write_file` now uses `safeWriteTarget` (`define.ts:99`). The checks are in `$S/rr24/runs/denylist.out`.

**Refused, correctly:**
- `.lumen/…`, `./.lumen/x.md`, `.Lumen/x.md`, `notes/.LUMEN/x.md`;
- `a/../.claude/x.json`, which `..` already refuses;
- `CLAUDE.md` in any case, and `sub/CLAUDE.md`;
- `AGENTS.md`, `GEMINI.md`, `.cursorrules`, `.mcp.json`;
- absolute, drive and UNC paths.

**Allowed but harmless:** Unicode look-alikes (a fullwidth dot, a Cyrillic С, a zero-width space). They name different files, and no file system folds them together.

**Gaps:**
- **`set_frontmatter` bypasses the deny-list.** It is a declared write tool and still uses `safeWorkspacePath` (`workspace.ts:282`). In rr24 (g1), one skill staged:
  - an `allowed-tools` change to `.lumen/skills/helper/SKILL.md`;
  - a frontmatter block added to `CLAUDE.md`.

  The review screen still applies. Editing a skill changes its fingerprint, so that skill asks again.
- **Names missing from the list:** `CLAUDE.local.md` (Claude Code loads it), and `AGENTS.override.md`, which Codex probably reads (not checked).
- **Windows spellings:** on Windows, `CLAUDE.md.`, `CLAUDE.md `, `CLAUDE.md::$DATA` and `CLAUDE~1.MD` all reach `CLAUDE.md`. OPFS stores them as written, so this matters only for the desktop backend.

**Fix:**
- Use `safeWriteTarget` in `set_frontmatter` and in every write tool.
- Add the missing names.
- Before matching, strip trailing dots and spaces and refuse names with `:` or `~`.
