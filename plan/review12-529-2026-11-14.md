## New paths

### U2 (medium, availability): the lock-then-build wait never ends after a vault switch

**Where:** `build()` waits only for `lumen-vault-unlocked` (`:142-146`, `:423`), and it does so inside `cache.inflight`. `ensureIndex` waits on `inflight` before its own switch check acts.

**Scenario:**
1. The encrypted vault is locked.
2. The open starts and waits for unlock.
3. The user switches to another vault, for example because they don't remember the passphrase.
4. Every `checkedIndex` query (search, backlinks, tasks, note text, embeds) now hangs until the page is reloaded.

**Test:** rr12 (l) FAILs: the search on the plain vault returns `"TIMEOUT"`.

There is also a narrow lost-wakeup: the listener is registered after the awaited state read. If the unlock event fires in between, the open waits forever.

**Fix:**
- End the wait on a vault switch, a `dropIndex` or an `epoch` change too, or poll `vaultEncryptionReady()`.
- Register the listener before reading the state.
- Re-evaluate the active vault after waking up.

### U1 (low): a vault switch during the first build, with equal mtimes

**Where:**
- The drop on a switch requires `cache.builtAt` (`:621`, `:677`). That is still 0 during the first build, even though `filledVault` is already set (`:435`).
- `fillEngine` reads the listed paths through whichever vault is active at the moment.

**Scenario:**
1. The first build starts on plain vault P and lists P.
2. The user switches to encrypted vault E mid-build, so the build reads E's notes at the shared paths.
3. The result is labelled P with `filledEncrypted` false.
4. Normally the follow-up refresh sees mtimes that differ, re-reads the notes and marks the index (rr12 j holds).
5. When the mtimes are equal, nothing is re-read. After the user switches back to P, the idle save writes **E's notes in the clear under P's id**.

**Test:** rr12 (j2) FAILs: `{"v":1,"vault":"vault-P","paths":["s/n0.md",…` with ESECRET.

This is contrived, because a conversion rewrites mtimes.

**Fix:**
- Drop whenever `filledVault` is set and differs, with no `builtAt` condition.
- In `build()`, throw the result away when `snapshotVault() !== cache.filledVault` after the reads.

### U3 (low): a lock during the build's own `clear()` leaves texts in the engine

**Where:** `dropIndex` clears the engine asynchronously. The build posts its restore after its `await eng.clear()`, and the keys were captured before the lock.

**Scenario:** when the lock lands inside that await, the restore runs after the drop's clear.

**Test:** rr12 (m) FAILs: 8 texts are left in the engine while the vault is locked.

This is **not reachable through any query**, because they all wait for unlock, and the next build clears it.

**Fix:** check `epoch` immediately before each post (the restore and the upserts), and clear again when it has moved.

### The other questions

**An index dropped mid-query:**
- `indexedNotes` filters its answer through `byPath`, so it returns nothing after a drop.
- A search that was already posted could still return its answer. In rr12 (q) it hung instead: the lock happened before its `ensureIndex` finished. No text was returned.

**A vault switch racing a worker restore:** `snapshotMode` checks `filledVault` against the active vault, so a restore is never attempted with the new vault's mode for the old index. The remaining case is U1.

**`checkedIndex()` bypassed:**
- `indexedFiles()` (summaries) is bypassed by design (T7).
- `indexStats()` returns counts only.
- I found no other export that reads text without it.

**T3 header re-check raced:** covered by the T6 post-check (rr12 p).
