## Z1 (high, pre-existing): a stale save writes vault E's plaintext as vault P's plain record

**What happens:**
1. P (plain) is being built. The user opens E (encrypted, already unlocked this session). The drop at `workspaceIndex.ts:894` fires and the build gives way.
2. `ensureIndex` still runs its follow-up `refresh()` rounds (`:851`), because the switch set `stale`.
   - The refresh lists and reads **E**'s notes into the engine while `filledVault` is null.
   - `applyChanges` raises `filledEncrypted` (`:785`) and schedules a save (`:797`).
3. The user goes back to P within 5 s.
   - There is no drop, because `:832` and `:894` need `filledVault !== null`.
   - The save timer survives, because `snapshotGen` moves only in `dropIndex` (`:217`).
4. P's next build sets `filledEncrypted = false` (`:602`) and `filledVault = P` (`:605`) **before** it clears the engine (`:643`).
   - After any failed check (`distrust`), that build waits for the whole listing first (`:640`).
5. The stale save lands in that window. `snapshotMode()` sees P, which is plain, filled from P and not encrypted, so the save writes the engine's contents in the clear under P's key.

**Tests:**
- **rr22 (z1):** a forced rebuild, with the save called by hand at the listing.
  ```
  engine after the stray refresh: "# s 1\nESECRET-1" | record sealed: false | ESECRET in clear: true
  | key: desktop:ab06… | contents[1]: "# s 4\nESECRET-4"
  ```
- **rr22 (z1b):** the production path, with nothing called by hand.
  - P's trusted open has a check whose listing fails (an I/O error), which sets distrust.
  - The rebuild gives way to E, the user goes back to P, and P's listing is slow.
  - The **real** 5 s idle save writes the record. Result: `save seen: true | ESECRET in clear: true`.

**Preconditions:**
- E is unlocked. T5 keeps the keys of a vault that was unlocked earlier.
- The user switches away and back within about 5 s.
- P's rebuild does not clear before the timer fires. That is certain after a failed check on a slow vault; on the trusted path it is only a narrow race, which I did not test.

**Fix:** any of these, ideally the first two together.
- Don't run the follow-up rounds after a build that gave way: stop when `!cache.builtAt || cache.filledVault !== snapshotVault()`.
- At the start of `build()`, cancel any scheduled save (`snapshotGen++`, clear `snapshotTimer`). Clear the engine before `filledEncrypted` is lowered or `filledVault` is set.
- Drop on every vault switch (a token of the last vault seen), not only when `filledVault` is set.

## The questions

### 1. Any other path to plaintext?

**Same-kind vaults:** j3 and rr19 y6 hold. Z1 remains, for any kinds.

**Fallback key (read-only `.lumen`)** (z2, PASS):
- E (encrypted) and P (plain) both file under `"desktop"`.
- P refuses E's sealed record and builds in full. Nothing goes out in the clear.
- The cost is that the two vaults keep deleting each other's record, which is perf only.

**Shared UUID** (synced copy, E encrypted later; z3, PASS):
- E refuses P's plain record (fromSnapshot 0) and finds no plain text.
- E's own record is sealed, and P then takes nothing from it.

**`vault-id` that an attacker or sync tool controls:**
- **Traversal text** (z4b, PASS): the content is never used as a path, and the key isn't built from it, because the regex at `:445` rejects it. Nothing else is read.
- **Non-UUID content is silently replaced** (`:449-452`). That's Z4, info.
- **Desktop symlinks:** Rust `resolve()` refuses links out of the root, and `write` renames a temp file onto the name, so a planted link is replaced rather than followed.
- **A planted or copied id** (z4, FAIL, info: Z2): the other vault's **plain** record is restored where path, mtime and size match ("ASECRETTEXT-2" shows in B).
  - The sealed side is safe, because the header's vaultId and the mode both have to match.
  - The docs sentence "so two folders never share a saved index" is not true for copies.

**First-write race** (z5, PASS): a switch while A's id is being written. Builds are serialised through `inflight`, and `recordVault` uses the backend it captured, so B's record is filed under B's own id and holds none of A's text.

Two tabs that write the id at the same time each cache their own UUID. The one that loses refuses its record at the next session: perf only.

### 2. Does Y1 hold?

Yes, for every announced change:

| Test | What happens | Result |
|---|---|---|
| rr19 y1 | a save during the check | PASS |
| z6a | a save, then a delete | not reused (2 listings), texts right |
| z6b | a content event with paths | re-read after the reuse |
| rr19 y2, Round6 | a structural event or a switch | the kept listing is dropped (`:906-907`) |

**Residue (Z3, info, z6c FAIL):** a change that raises no event, such as another tab on the same OPFS, keeps the old text until the 30 s revalidation. A fresh listing could miss it too. The kept listing only widens that window, up to the check timeout.

### 3. Do the guards survive a reload or reconnection of the same vault?

- **A new object for the same vault** (re-picking a desktop folder, OPFS after `setVaultBackend(null)`) is a **false drop** only: one rebuild, the same record key, and the next open restores from the snapshot (z7: hits 6, key unchanged, fromSnapshot 6).
- **A folder reconnect** keeps the same object, so its token doesn't change.
- **No false keep:** no backend mutates its root. Tauri's root, the folder handle and the mobile store are fixed per object, and a re-gate keeps the inner object.

### 4. Are old kind-only records refused?

Yes. A forged `"folder"` record is refused and deleted. The notes are read (fromSnapshot 0, real text), and the new record is filed under `folder:<uuid>` (z8).

The one exception is the fallback case, where the key is the kind again and an old record is still accepted. The listing still checks it, so the behaviour is as before.
