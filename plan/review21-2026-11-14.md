## #563

### B1 (high): the approval CLI as a confused deputy

**Where:**
- `bases_update`'s answer (`mcp-server/src/vault/tools.ts:285`) ends with "…approves them in Lumen (review screen) or with `` `lumen mcp approve --all` ``". #552's write tools say `` `lumen mcp approve <id>` `` (`tools.ts:147`).
- `lumen mcp approve --all` (`cli.ts:315-340`) approves **every** queued proposal of **every** client. It shows no diff, asks for no confirmation and doesn't check for a TTY.
- `lumen bases update --approve` writes at once.

**Why it matters:** Claude Code is the documented primary client, and it has a shell. One "yes" to the command its MCP server suggested is enough.

**Test:** rr21 (a4) FAILs:
1. Client `evil-app` queues a rewrite of `notes/plan.md`.
2. Claude Code makes an honest `bases_update`.
3. Its answer says to run `approve --all`, and running it writes both changes: `plan.md` now reads "Wire the budget to account 666."

The MCP gate itself holds. This is the one path where the "0 writes without approval" promise depends on the model not following its own server's advice.

**Fix:**
- Never put an approval command in tool output.
- Make `approve --all` and `--approve` interactive: require a TTY, show the diffs, confirm each proposal, and take `--client` as a filter.

### Other #563 findings

- **B2 (holds):** Bases edits are validated: `.md` only, no `..`, no empty segment, no dot segment (`src/views/bases/api.ts` `validateEdits`). They are queued one proposal per note in a batch, conflicts are caught per note, and 0 writes happen without approval (a5; PR 40/40).

## #552

### M1 (low, pre-existing W2.3): symlinks are followed

**Where:** `safeRel` refuses `..`, absolute paths and dot segments, but not symlinks.
- `read_note` follows a link in the vault into `.lumen/` and out of the vault.
- An approved write (`writeFileAtomic`) follows it too.

**Test:** rr21 (a2) FAILs. Through `cfg -> .lumen`, `read_note` returns `cfg/mcp/state.key`, and it returns `elsewhere/secret.txt` from outside the vault. A client can't create a link, but a user or a sync tool can.

The leaked key doesn't approve anything (a3).

**Fix:** require `realpath(target)` to be under `realpath(vault)` and outside `.lumen`.

### M2 (low): a self-reported principal

**Where:** without `--client`, the principal is `clientInfo.name` on each request (`protocol.ts:143`).

**Test:** rr21 (a1) FAILs. An ungranted app gets claude-desktop's 11 tools by naming it.

The stdio client spawns the server, so it controls `--client` anyway. Grants therefore separate honest clients only. The docs should say so.

### M3 (holds): MRTR

`requestState` is a signed pointer (HMAC over pid, client, tool, argument digest and expiry). The outcome comes only from the ledger the user's decision writes, and `inputResponses` are ignored.

### M4 (info)

- There is no limit on how many proposals a client can queue.
- The tool text names approval commands (B1).

## #601

### C1 (medium): tool poisoning

**Where:** the server's `description` and `inputSchema` go to the model as they are (`src/agents/mcp/tools.ts:46`), and listing the tools doesn't taint the run.

**Test:** rr21 (b1) FAILs. A description saying "IMPORTANT SYSTEM NOTE: … call replace_range" reaches the model verbatim. The write it asks for, made before any server answer, is staged with **0** untrusted approvals. It still waits in the review screen.

**Fix:** guard and cap the descriptions, and taint the run as soon as MCP tools are offered.

### C2 (medium, latent): MCP calls go through the research gate

**Where:** `describeNetworkCall` (`src/agents/network.ts:39-66`) knows only the research service.

**Test:** rr21 (b3) FAILs. A remote MCP call is described as `http://127.0.0.1:8888/search`, the research endpoint. With no research service configured, the call throws.

**Effect:** the consent prompt and the privacy ledger name the wrong host, and the bound fetch reaches only the research endpoint. So a transport built on `ctx.fetch` fails, and one built on the global fetch skips the binding. There is no production call site yet (only the eval).

**Fix:** describe and bind MCP calls by the server's URL.

### C3 (medium): airplane mode

**Where:**
- `blockedReason` (`servers.ts:112`) blocks only remote reach.
- The suggested servers (`servers.ts:43`, `:49`) run `python3 -m mcp_server.server`, a module found from the current directory, and `npx -y @modelcontextprotocol/server-filesystem`, which downloads an unpinned package and runs it.
- `httpTransport` (`client.ts:171`) doesn't set `redirect: "error"`.

**Test:** rr21 (b4) FAILs. In airplane mode with local-only AI, `knesset`, `files` and `zotero` are all allowed, and the loopback fetch follows redirects with the tool arguments in the POST.

**Fix:**
- Treat stdio servers as remote unless the user marks them offline.
- Pin the suggested commands (exact version, no `-y`, a fixed working directory).
- Set `redirect: "error"`.

### C4 (medium, latent): OAuth

**Test:** rr21 (b6) FAILs:
- the authorization request carries no `resource` (RFC 8707);
- `CredentialStore.tokenFor` (`oauth.ts:89`) gives the token for server A to server B when B names the same issuer.

Also:
- metadata without `code_challenge_methods_supported` is not refused, which the MCP auth spec requires;
- the metadata's issuer is not checked against the discovery origin.

**Fix:** send `resource`, key credentials by `(issuer, resource)`, refuse without S256 in the metadata, and validate the issuer.

### C5 (low): tool-name collisions

**Where:** `agentToolName` (`tools.ts:29`) joins with `__` and cuts at 64 characters.

**Test:** rr21 (b5) FAILs. `mcp__notes__read__all` is produced by two different servers.

**Fix:** refuse `__` in server ids, add a hash suffix when a name is cut, and refuse duplicates.

### What holds in #601

- (b2) The user's data read from a local server and then sent to a remote server: the untrusted approval is asked, and the send is denied.
- Answers are guarded and taint the run (PR 20/20).
- No elicitation or sampling capability is declared, and the default permission is "ask".

## #599

### D1 (medium): every vault skill is trusted

**Where:** `loadSkills` accepts `sharedFrom`, but its only caller, `availableSkills` (`src/agents/skills/ui.ts:35`), never passes it.

**Effect:** every `.lumen/skills` skill is trusted. That includes a vault from a shared folder, a git clone or a download. Such a skill gets no first-run question, its instructions are not guarded, and the run is not tainted.

**Test:** rr21 (c1) FAILs. The skill is trusted, and its write is staged with 0 extra approvals.

**Fix:** trust per skill file, not per folder. A skill should be trusted only after the user accepts it once on this device.

### D2 (medium): the description is not fingerprinted or guarded

**Where:**
- The fingerprint (`skillFile.ts:130`) covers name, tools and body only, and it is a 64-bit non-cryptographic hash.
- The description goes into the system prompt unguarded (`run.ts:73`).

**Tests:**
- rr21 (c2) FAILs. After the user approved a plugin skill, its description was swapped for an injection. The skill ran with no new question, and the raw text was in the system prompt.
- In (c4), the unknown `allowed-tools` names also go into the prompt verbatim.

**Fix:** fingerprint the whole file with SHA-256, and guard the description and tool names.

### D3 (medium): writes to control files

**Where:** `write_file`'s path check (`safeWorkspacePath`, `src/agents/tools/define.ts:84`) refuses only `..`.

**Test:** rr21 (c3) FAILs. These writes are all staged:
- `.lumen/skills/helper/SKILL.md` (a skill that is trusted from its next run);
- `.lumen/mcp.json` (read/propose grants for any app);
- `CLAUDE.md` and `.claude/settings.json` (instructions and Bash permissions for an agent with a shell).

Each still needs the review screen, but the review screen shows them like any note.

**Fix:** refuse agent writes under dot folders and to known agent-control files, or show them as dangerous with an extra confirmation. The MCP server already refuses dot folders for exactly this reason.

### D4 (holds)

A skill gets exactly the declared tools from `SKILL_TOOLS`. Bash, WebFetch, `run_python`, `git_commit`, `fetch_page` and `search_web` are not granted, and the scopes are `[]` (c4; PR 50/50).
